# Build Actions YAML Handoff

The downstream `build-actions-generator` skill consumes this skill's
`migration.warnings` and `migration.notes` arrays to emit
`.build-actions/config.yaml` for the Capacitor plugin. The Build Actions
YAML is what ODC mobile builds apply (via Advanced Extensibility) at
`cap sync` time on MABS 12+. Plugin authors do not hand-write
`.build-actions/config.yaml`; the generator skill produces it from the
classified hints the migrator emits.

## Three Destinations for Every plugin.xml Directive

For every `<config-file>`, `<framework>`, `<preference>`,
`<source-file>`, etc. in the Cordova `plugin.xml`, classify into one of
three downstream buckets:

| Bucket | What goes here | Where it lives |
| --- | --- | --- |
| **Plugin packaging** | AndroidManifest `<uses-permission>` / `<meta-data>` / `<queries>` / `<provider>`; Gradle deps and custom Maven repos; CocoaPods deps; system / weak / vendored iOS frameworks; `@CapacitorPlugin(permissions = [...])` annotations; FileProvider XML resource files; bridging headers | Plugin's own `android/build.gradle`, `android/src/main/AndroidManifest.xml`, `android/src/main/res/`, `.podspec`, `Package.swift`, `ios/Sources/` |
| **Build Actions YAML** | Info.plist privacy strings; iOS capabilities + entitlements; host-app resource drops (e.g. `<Plugin>Configuration.json` placed in `ios/App/App/json-config/`); host-app-level manifest mutations to the `<application>` element that Gradle manifest merger cannot supply | `.build-actions/config.yaml` (generated by `build-actions-generator`) |
| **Consumer runtime config / code** | Apple Developer-side credential provisioning (merchant IDs, API keys); host-app-supplied JSON config values that the plugin reads at runtime; consumer JS call-site migration (callback → Promise, positional → named) | Consumer's own codebase + Apple/Google developer portals |

## Decision Flow

For each `plugin.xml` directive, ask in this order:

1. **Can the plugin's own package express it?**
   - Gradle `implementation '...'` → plugin's `build.gradle` ✅
   - CocoaPods `s.dependency '...'` → plugin's `.podspec` ✅
   - AndroidManifest `<uses-permission>` / `<meta-data>` → plugin's `AndroidManifest.xml` ✅ (Gradle manifest merger applies)
   - Runtime permission flow → `@CapacitorPlugin(permissions = [...])` annotation ✅

   If yes, classify as **plugin packaging**. Done.

2. **Is the value the same for every consumer (constant)?**
   - Info.plist privacy string with a fixed message string → **Build Actions YAML**
   - Capability toggle with a static entitlement value (e.g. `aps-environment = development`) → **Build Actions YAML**
   - Always-on iOS capability (Apple Pay enabled) → **Build Actions YAML**

3. **Does the value differ per consumer?**
   - Apple Pay merchant ID, OAuth client ID, analytics key, custom backend URL → **Runtime config JSON file** (preferred) or per-consumer Build Actions overrides (last resort)
   - Apple Developer account provisioning steps → **Consumer runtime / external** (no tool can automate)

## When the Cordova Plugin Already Uses Runtime Config

If the Cordova plugin already ships a hybrid `capacitor:sync:after`
script that copies a `<Plugin>Configuration.json` file into native
projects at sync time (the OutSystems Payments pattern), **reuse it**.
Record under `migration.notes`:

```yaml
migration:
  notes:
    - "Hybrid `capacitor:sync:after` script `hooks/capacitorCopyPreferences.js` already copies `PaymentsPluginConfiguration.json` into `ios/App/App/json-config/` and `android/json-config/`. The Build Actions YAML must declare ONE resource entry pointing at the consumer's `$extensibilitySettings.PaymentConfiguration` source; the runtime values (merchant ID, country code, allowed networks, etc.) all live inside the JSON file. No per-value Info.plist entries needed."
```

This collapses 12+ would-be Info.plist entries into 1 Build Actions
YAML resource entry plus a consumer-side JSON file.

## Recording Hints for `build-actions-generator`

Emit each Build Actions YAML candidate as a `migration.notes` entry
prefixed with `build-actions:` so the downstream skill can grep for
them. Example:

```yaml
migration:
  notes:
    - "build-actions: iOS Info.plist NSLocationWhenInUseUsageDescription = 'This app uses your location to show nearby points of interest.'"
    - "build-actions: iOS capability com.apple.developer.in-app-payments with merchant ID from $extensibilitySettings.ApplePayMerchantId"
    - "build-actions: resource $extensibilitySettings.PaymentConfiguration -> ios/App/App/json-config/PaymentsPluginConfiguration.json (and android/json-config/ equivalent)"
    - "plugin-package: AndroidManifest <uses-permission android:name='android.permission.VIBRATE'/> goes in plugin's own AndroidManifest"
    - "plugin-package: Gradle implementation 'com.google.android.gms:play-services-wallet:19.1.0' goes in plugin's own build.gradle"
    - "consumer-runtime: Apple Developer-side merchant ID provisioning. No tool can automate."
```

The `build-actions-generator` skill ingests every `build-actions:` line
and produces the YAML file; everything else is informational for the
generator / human reviewer.

## Counting Effort for Reviewers

When summarizing remaining effort for a migration plan, count Build
Actions YAML at **file granularity, not entry granularity**:

- 0 Build Actions YAML files = plugin needs no host-app config beyond
  what plugin packaging provides (true for `cordova-plugin-vibration`).
- 1 Build Actions YAML file = plugin needs one or more host-app config
  artifacts (Info.plist privacy strings, capabilities, resources).
  The downstream skill produces this one file regardless of whether it
  declares 1 entry or 30.

The reviewer's mental cost is "one YAML file the generator skill
produces, applied automatically by ODC." Not 22 distinct manual edits.

## Anti-Patterns

- ❌ Emitting an `migration.warnings` entry for every Info.plist key,
  every Gradle dep, every Manifest line. The `migration.warnings` array
  is for things the human reviewer must know; routine config goes in
  `migration.notes` for the downstream skill.
- ❌ Putting `implementation '...'` Gradle lines in `MIGRATION.md` and
  asking consumers to add them. Deps go in the plugin's own
  `build.gradle`; consumers get them transitively via `cap sync`.
- ❌ Writing static Apple Pay merchant configuration into the Build
  Actions YAML. Use the runtime config JSON pattern so each consumer
  supplies their own.
- ❌ Asking consumers to "enable Apple Pay in Xcode" in `MIGRATION.md`.
  The Build Actions YAML declares the capability; ODC enables it at
  build time.
